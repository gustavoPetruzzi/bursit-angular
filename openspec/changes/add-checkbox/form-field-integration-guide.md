# PR 2 — Checkbox FormField Integration (Phases 3-5)

Branch: `feat/add-checkbox-form-field` (created from updated `master`, which already contains the merged PR 1 core).

Goal: integrate `bursit-checkbox` with `bursit-form-field` so the field wrapper reacts to the checkbox state (error, disabled, focus, hover, required) and the checkbox wires `id`/`aria-describedby` with the field's generated IDs.

## Phase 3 — Tests to write (RED)

Add a `describe('Checkbox in FormField')` block to `projects/bursit-angular/src/lib/forms/checkbox/checkbox.spec.ts`.

### Harness

Create a wrapper component (mirror the pattern from `input.directive.spec.ts`) that renders:

```html
<bursit-form-field>
  <bursit-checkbox [formControl]="control" validationInteraction="touched">
    Acepto términos
  </bursit-checkbox>
</bursit-form-field>
```

- Control: `new FormControl(false, [Validators.requiredTrue])`.
- Imports in the wrapper: `ReactiveFormsModule`, `FormField`, `Checkbox`.
- Query helpers you'll need: `By.directive(Checkbox)` for the checkbox debug element, `By.directive(FormField)` for the form-field host element.

> **Key detail**: a checkbox `required` is validated with **`Validators.requiredTrue`**, NOT `Validators.required`. Angular's `required` only fails on empty values (`null`/`undefined`/`''`) and `false` is not empty — an unchecked checkbox would stay "valid" with `required`. `requiredTrue` demands exactly `true`.

### Test scenarios (write these, they must FAIL initially)

1. **Initial state — no error class**: with `validationInteraction="touched"` and the control empty+required and untouched → the form-field host element does NOT have class `bursit-form-field-error`. (Assert `control.invalid` is `true` and `control.touched` is `false` to prove the scenario setup.)

2. **Error class after touch**: same control → dispatch `focus` then `blur` on the native input, then call `control.markAsTouched()`, then flush microtasks (the double `queueMicrotask` pattern from `input.directive.spec.ts`) → the form-field host element DOES have class `bursit-form-field-error`.

3. **`aria-describedby` wiring**: with the checkbox inside the form-field and no user-set attribute → the native input's `aria-describedby` equals `${fieldId}-error ${fieldId}-message`, where `fieldId` is the input's own `id` (the checkbox writes it; derive the expected value from `input.id`).

4. **Disabled propagation**: control starts enabled → form-field host does NOT have `bursit-form-field-disabled`; call `control.disable()` + `fixture.detectChanges()` → the form-field host DOES have `bursit-form-field-disabled`.

## Phase 4 — Implementation steps (GREEN)

Apply these to `checkbox.ts` (and one line to `checkbox.html`). Each step is the "what" — mirror the repo patterns cited for the "how".

### 1. Add `FormFieldControl` to `providers`

Why: `<bursit-form-field>` finds its control with `contentChild(FormFieldControl)` — a DI token query, not a CSS selector. Without providing yourself as `FormFieldControl`, `formFieldControl()` is `undefined` and every state class on the field host (error, disabled, focus, hover, required) never applies. `NG_VALUE_ACCESSOR` is Angular Forms' value contract; `FormFieldControl` is the library's visual-state contract — both needed.

Pattern: mirror the provider block in `select.ts` (`provide: FormFieldControl, useExisting: forwardRef(() => Select)`), keeping your existing `NG_VALUE_ACCESSOR` provider.

### 2. Add `FormFieldControl<boolean>` to `implements`

Why: compile-time guarantee of the contract promised in step 1. DI is blind; TypeScript catches missing members at build time instead of runtime crashes.

### 3. Add `readonly invalid = signal(false)`

Why: the visual error state the form-field reads via `formFieldControl()?.invalid()`. Must be a signal (contract says `Signal<boolean>`) because the form-field is `OnPush` — signal reads in template bindings mark the consumer for re-render. This is where `validationInteraction` finally matters.

### 4. Inject `NgControl` and `FORM_FIELD_ID`

- `control = inject(NgControl, { self: true, optional: true })` — bridge to the real FormControl. `self: true` prevents grabbing a parent form's `NgControl`; `optional: true` lets the checkbox work standalone.
- `private _fieldId = inject(FORM_FIELD_ID, { optional: true })` — the id generated by the form-field (`bursit-field-N`); needed to wire `id`/`aria-describedby` with the field's `${fieldId}-error` / `${fieldId}-message` slots.

Pattern: `select.ts` lines 52-53.

### 5. Add a `viewChild` for the native input + `#input` in the template

Why: the class needs the real `<input>` DOM element to write `id` and `aria-describedby` at runtime. Not available until `ngAfterViewInit`.

Pattern: `select.ts` line 104 (`viewChild.required<ElementRef<HTMLElement>>('trigger')`); for the checkbox a plain `viewChild<ElementRef<HTMLInputElement>>('input')` + `?.` suffices since the wiring is optional.

### 6. Constructor: `if (this.control) this.control.valueAccessor = this;`

Why: the `valueAccessor` property is what `FormControlDirective` actually consults for `writeValue`/`registerOnChange`/`registerOnTouched`. Assigning directly guarantees the connection regardless of DI resolution order.

Pattern: `select.ts` constructor (lines 125-129).

### 7. `ngOnInit`: initial sync + subscriptions

Why: snapshot covers state the control was born with (already disabled/invalid — `statusChanges` does not emit without a transition); subscriptions (`valueChanges` + `statusChanges`) cover external changes (`setValue`, `patchValue`, `reset`, `disable`, validity flips). Both events needed: `disable()` changes state not value; `setValue(true)` changes value not state.

Pattern: `select.ts` `ngOnInit` (lines 135-148), storing subs in a `Subscription[]`.

### 8. `ngOnDestroy`: unsubscribe all

Why: the checkbox dies with the view (`*ngIf`, routing, `ngFor`) while the FormControl lives on — without `unsubscribe()` you leak listeners calling `_syncFromControl()` on destroyed objects.

Pattern: `select.ts` `ngOnDestroy` (lines 156-158).

### 9. `_syncFromControl()` + `_isInvalid()`

Why: the sync engine. `invalid` is computed (never copied raw) through `_isInvalid()` — filtering `control.invalid` by `validationInteraction` (if `'touched'`, also require `control.touched`). `disabled` is copied directly with `|| false` as a type guard (`control` is `any` in the contract).

Pattern: `input.directive.ts` `isInputInvalid()` (lines 124-138) and `onValueChanges()` (lines 140-144).

### 10. `onBlur`: add `queueMicrotask` re-check of invalid

Why: browser event order — your `onBlur` runs BEFORE Angular's `DefaultValueAccessor` calls `markAsTouched()`. Reading `control.touched` synchronously would see `false` and the error would never show. `queueMicrotask` defers the re-check until after `markAsTouched`, before paint. Only matters for `validationInteraction='touched'`. Keep your existing `this.onTouched?.()`.

Pattern: `input.directive.ts` `onBlur` (lines 68-76).

### 11. `ngAfterViewInit`: `_wireId()` + `_wireAriaDescribedBy()`

Why: writes `id="${fieldId}"` on the native input (so the form-field's `bursitLabel` `for` — generated by `LabelDirective` — points at the checkbox) and `aria-describedby="${fieldId}-error ${fieldId}-message"` (screen readers announce the field's error/helper slots). Both guarded by `!userSet && this._fieldId`: never overwrite user-set attributes, only wire inside a form-field. Must run in `ngAfterViewInit` because that is when `viewChild` resolves.

Pattern: `input.directive.ts` `_wireId`/`_wireAriaDescribedBy` (lines 99-114) — copy the exact logic, reading the input from your `viewChild` instead of `this.el`.

### What NOT to implement (design decision 6)

`floatingLabel`, `hasPlaceholder`, `hasValue`, `type` — the checkbox never floats its label. The form-field already falls back to `?? !!control?.value` for the `has-value` class.
